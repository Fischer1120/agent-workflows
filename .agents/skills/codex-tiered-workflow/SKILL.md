# 分层档位协作工作流

用户当次要求优先。本技能只分配已获授权的工作，不扩大项目、权限或外部操作范围。

## 问题查询与记录

将 [project-corrections](../project-corrections/SKILL.md) 作为本工作流的查询与记录入口。该技能导入 [索引](../../../docs/corrections/index.md) 和 [完整记录](../../../docs/corrections/records.md)，案例正文只维护在完整记录中，不逐条追加到技能指令。

主窗口开始任务时加载该技能和索引。仓库内按上述相对路径定位记录库；安装后按安装器写入的实际路径定位。跨项目使用时以已安装入口为准；其他项目的问题注明真实来源与适用范围，不在当前目录另建同名副本。入口缺失或无权访问时说明具体阻碍，继续原任务中可安全执行的工作；未完成的查询或同步必须在简报中说明。

主窗口或执行者遇到报错、异常、返工、用户纠正，或准备重新实现已有方法时，必须先用该技能查询，再尝试新的解决办法。阅读命中条目全文，核对范围、环境、版本与权限，最小复验适用且已验证的方案后优先复用。没有匹配或方案不适用时再正常排查，并保留必要的原始问题与验证回执，供最终检查回顾；无需为没有实际问题的任务编造条目。

## 档位划分

按模型能力档位分工，模型名称是可替换的参考实现。换用同类模型时按档位对应，不因具体型号不同改变分工。

| 档位 | 参考模型 | 承担的工作 |
| --- | --- | --- |
| 旗舰档 | `gpt-6.1-sol`、Claude Opus、Gemini 4 或其他旗舰模型 | 日常主窗口。需求与验收标准、任务分解、模型分配、前端设计、架构与关键决策、结果整合，以及普通任务的最终独立审查 |
| 中档快速档 | DSH（DeepSeek），模型以部署机器实时 catalog 为准 | 中等复杂度、边界明确、需要快速处理的非多模态任务；DSH 内发起的低成本任务；宿主没有低端档位时承接原本给低端模型的快速任务 |
| 低端快速档 | `gpt-6-luna`（`max`，Fast）、Claude Haiku 等 | 简单、重复、可独立核验的快速任务：检索、提取、批量小修改、固定规则检查 |
| 原生中坚子代理 | `gpt-6.1-terra` 或其他原生子代理，可选 | 旗舰档判断适合交给原生子代理承担的有界执行任务 |
| 攻坚档 | `gpt-6-astra` 或同类最高推理档专项子代理 | 旗舰档经针对性分析仍无法解决的十分复杂问题，尽量少用 |

旗舰档的推理档位保持较高设置（Codex 中为 `xhigh`），低端档使用各自的最快档（Luna 固定 `max` 加 Fast）。主窗口速度档位不因下放任务而改变。

## 路由顺序

先判断模态，再按复杂度与时限分流，能力不足时才考虑攻坚档。

1. 模态优先。需要理解或生成图片、音频、视频，或需要查看截图、扫描页、图表及实际渲染效果的，不交给 DSH，也不交给低端档。由旗舰档选择实际支持所需模态及工具的原生执行者执行，成品交给未参与实现的独立旗舰子代理验收。只有能明确拆出、不依赖多模态材料和结论的纯文本或代码子任务，才可以按后面的规则分流，不能把多模态任务转述成文字来绕开限制。
2. 简单快速的重复任务交低端档。检索、提取、批量小修改、固定规则检查这类工作，判断难度低、结果可独立核验，适合低端档承担。
3. 中等复杂度、边界明确、要求快速处理的非多模态任务交 DSH。模块实现、跨文件调试、集成验证和资料整理大多落在这一档。
4. 其余判断类工作留在旗舰档。前端视觉设计、架构取舍、业务含义、验收规则和最终取舍不下放。超出中等复杂度、边界还不清楚的工作先由旗舰档分析，再决定交给谁。
5. 旗舰档已做过针对性分析或验证仍无法解决的十分复杂问题，才考虑攻坚档。

任务分配按不确定性和判断难度决定，不能只看文件数量。

## DSH 内发起与低成本合并

任务原本就在 DSH 会话里发起时，省去 `scripts/dispatch.py` 的跨进程派发环节，直接在当前会话用原生子代理（`subagent` 或 Team 机制）分派有界子任务。原本属于低端档的简单快速任务同时合并到 DeepSeek 处理，不再调用外部低端模型脚本。这样省掉一次会话创建和回执轮询，也避免同一环境下重复登录和重复派发。

其他宿主没有可用的低端模型档位时，同样把低成本快速任务合并到 DeepSeek：从外部宿主发起时走 DSH 派发入口，在 DSH 内则直接原生处理。宿主确实提供低端档位时（例如 Codex 的 Luna `max` 加 Fast，或支持 Haiku 的原生子代理入口），优先用对应入口派发，不强行合并。

需要跨进程持久回执、状态查询或给其他宿主留验收记录时，仍然使用派发脚本。合并只针对派发成本高于任务本身的小任务，不改变权限范围，也不放宽任何模态或验收要求。

DSH 内发起、又拿不到旗舰档子代理的普通任务，由未参与实现的独立 DSH 子代理按同等要求只读验收，交付时说明这一限制，不能把执行者的自检当成独立验收。

## 非多模态速度优先任务

用户明确强调速度、紧急交付，或已明确时限使速度成为首要约束时，使用速度优先模式。不能仅凭执行者方便或模型已有 Fast 档就擅自认定。

从外部宿主发起的非多模态速度优先任务交给 DSH 执行，成品由未参与实现的另一个 DSH 会话只读验收。旗舰档只保留目标、边界、必要关键决策和协调，交付时汇总验收证据，不重新执行同一套验收。DSH 内发起的同类任务由未参与实现的独立 DSH 子代理验收。业务和权限问题仍由旗舰档接回，攻坚档启用条件不变。

## 接收与分派

先读用户指定的文件和项目指令，用简短约定记下目标、范围、产物和验收方式。真正影响结果的缺口集中问清楚；提问期间继续独立工作。长任务使用项目已有任务记录，确需新文件时放在当前任务目录，不写入全局记忆。

把有清晰边界的工作主动交给对应档位。每份简报包含目标、必要背景、输入路径、允许修改的文件、授权与约束、验收方式和回报格式。只传必要材料，不传完整聊天记录。前端任务由旗舰档先确定信息层级、视觉方向、关键交互、响应式布局以及空态、加载态和错误态的要求。

在执行者简报中附上 project-corrections 的实际路径、相关记录编号及先查询后处理的要求。执行者遇到问题时按需读取并回传原始问题证据、实际采用的办法和验证结果，由主窗口合并记录，不让多个执行者同时改写索引和正文。

旗舰档、攻坚档和原生子代理通过当前宿主的原生子代理工具派发，传入实际模型标识和独立任务简报。不使用不存在的 backend 名称，也不借用创建用户侧新聊天的工具代替子代理。

从 Codex 等外部宿主派发 DSH 和低端档时，可执行入口在本技能的 `scripts/dispatch.py`。使用前可运行 `python3 .agents/skills/codex-tiered-workflow/scripts/dispatch.py --help`。先把简报写入文件，再派发：

```sh
python3 .agents/skills/codex-tiered-workflow/scripts/dispatch.py submit --backend dsh --cwd "/absolute/project" --project-title "项目标题" --task-title "子任务名" --brief-file "/absolute/brief.txt" --sandbox workspace-write
python3 .agents/skills/codex-tiered-workflow/scripts/dispatch.py submit --backend luna --cwd "/absolute/project" --project-title "项目标题" --task-title "子任务名" --brief-file "/absolute/brief.txt" --sandbox read-only
python3 .agents/skills/codex-tiered-workflow/scripts/dispatch.py status --job-file "/absolute/project/.workflow-runs/cw-.../job.json"
```

非多模态速度优先任务使用以下入口。未指定 `--backend` 时自动选 DSH；速度优先与 Luna 不能同时指定。执行完成后，将最终文件路径和验收要求写入另一份简报，再启动独立验收；不要转发实现会话的推理或预设结论。

```sh
python3 .agents/skills/codex-tiered-workflow/scripts/dispatch.py submit --speed-priority --phase execute --cwd "/absolute/project" --task-title "速度优先执行" --brief-file "/absolute/execute-brief.txt" --sandbox workspace-write
python3 .agents/skills/codex-tiered-workflow/scripts/dispatch.py submit --speed-priority --phase review --cwd "/absolute/project" --task-title "DSH 独立验收" --brief-file "/absolute/review-brief.txt" --sandbox read-only
```

本入口可用 `--multimodal` 显式声明多模态需求；声明后所有派发都会在读取简报、创建任务目录及调用后端前被拒绝，DSH 与低端档都不能绕过，速度优先执行和验收同样如此。该标记不自动识别简报内容，派发者仍须先判断模态；多模态任务应交给实际支持所需输入、输出和工具的原生执行者，不能省略标记绕过规则。

每次 `submit` 创建独立 DSH 会话。验收阶段必须只读；有实质问题时回传原执行者修复，再由 DSH 复验受影响部分。执行轮 `completed` 只代表执行结束，最终通过须有独立验收结论及实际检查证据。压缩简报、减少重复调查，保留完成要求所必需的检查；没有证据时不能为赶时间声称通过。

`--cwd` 必须是当前已授权的项目目录；需要编辑时明确使用 `--sandbox workspace-write`，只读任务用 `read-only`。DSH 的权限从实时 catalog 匹配同名预设，入口不提供 full-access 或 auto。

省略 `--project-title` 时，入口从本机 Codex 的项目记录中按真实目录匹配名称；没有匹配记录时使用目录名。名称匹配有歧义时显式传入当前项目标题。DSH 以相同的真实 `cwd` 创建或复用工作区，文件直接共享，工作区原有标题保留；任务简报和本地回执同时保存项目标题及子任务名。当前 Bridge 没有标题修改接口，不能声称 DSH 界面标题已同步。

入口复用 DSH 已安装的 Bridge，无需通过 DSH 的 `subagent_codex` 再把任务派回 Codex。默认 DSH 模型保存在相邻的 `workflow.json`；用 `dispatch.py discover` 查看实时模型和权限，旗舰档可用 `--dsh-model` 传入实际 catalog 的 selectionId。配置中的模型失效就回报，不静默改用其他模型。

原生子代理继承主会话的速度档位，因此低端档使用独立 app-server 入口，明确设置模型、推理强度和 Fast；服务端返回模型、推理强度和速度档位后才启动模型轮次。Fast 在当前运行时可能返回 `priority`。不要用未验证的全局设置或不能选择速度的 `collaboration.spawn_agent` 冒充低端档 Fast。

## 等待与异常处理

派发返回任务回执后，保留该任务的 `job_file` 和 sessionId，并定期用 `status` 查询同一任务。低端档的 `completed` 须有真实轮次结束通知；DSH 的 `completed` 须有当前轮 `turn.end` 且结果为 `done`，仅有 `idle` 不算完成。结果保存在回执目录的 `result.txt`。`needs_attention` 由旗舰档接回处理；权限不足不自动扩大权限。`submission_unknown` 表示投递状态不确定，先按回执中的同一 sessionId 查询 DSH，不能另建任务盲重试。

DSH 任务须等待当前轮真正完成、结果内容返回，并读取 `result.txt` 及必要产物后，才能基于其结果开展整合、验收或其他依赖步骤。在此之前，主窗口及其他执行者只处理与该任务无依赖、文件范围不重叠的并行工作；没有可并行的工作时就等待并查询状态。不得跳过 DSH 返回内容，不得依据预计结论、过程日志或尚未完成的文件推进后续步骤，也不得自行或另行派发重复调查、实现或验收同一任务。任务运行较久或暂时无新输出不构成接管理由。

DSH 不可用、未启动、模型未配置或任务失败时，回报具体阻碍。只有确认原任务不再执行，或用户明确要求中止且已完成中止后，旗舰档才可在原授权内接回分析或修复；接回前核对已有产物并明确剩余范围，避免重复工作。`needs_attention` 先处理请求或阻碍并确认任务状态，不能直接视为任务失败。不能悄悄换档、改模型或自动安装其他依赖。没有可用执行接口时如实说明。

## 并行与上下文

只在任务独立、工具允许且确有收益时并行；遵守当前并发上限。为各执行者分配互不重叠的文件，共享入口和集成修改由旗舰档串行协调。共享目录没有隔离效果，必须保留用户与其他执行者的修改。被派发的执行者只完成收到的简报，不递归重分配。

子代理使用当前工具支持的确切模型标识；优先 `fork_turns="none"` 并提供完整简报，只在必要时使用有限轮次。需要模型覆盖时不能使用完整历史 fork。

回报包含完成情况、结论、产物路径、实际验证结果、风险与待决事项。完整日志留在文件中，主窗口只读决策需要的片段。中低档执行者遇到业务判断、范围扩大、权限问题或测试失败，停止相关修改并回报旗舰档，由旗舰档决定下一步。

## 攻坚升级与最终验收

仅当旗舰档已完成有针对性的分析或验证，明确仍无法解决一个十分复杂的问题时，才自行判断是否调用攻坚档，并按该难题选择推理强度，优先考虑 `max`。升级前简要记录已尝试的方法、失败证据及需要攻坚档解决的具体问题，默认尽量少用。缺少资料、用户决策、权限或工具故障应先解决相应阻碍，不能直接视为模型能力不足。攻坚档只承担该难题的专项求解，解决后由旗舰档接回协调、决策与验收。

普通任务及多模态任务由旗舰档按约定检查关键证据，成品交给未参与实现的旗舰子代理独立审查。非多模态速度优先任务由未参与实现的 DSH 会话或独立 DSH 子代理完成同等要求的独立验收，旗舰档汇总证据，不默认追加一轮实质复核。两条路径都不能用实现者的自检冒充独立验收。成品检查只给审查者具体要求、成品及必要原始材料，不给制作过程、预期结论或先前审查意见。成品文档同时遵守用户的排版及语言规范。

最终独立检查同时包含问题回顾，无需用户再提醒。为此单独提供本次任务可核实的用户纠正、原始报错与验证回执，以及 project-corrections 入口；不传完整制作过程或制作者预设的复盘结论。审查者自行查找本次遇到的问题及实际给出的解决方法，与现有记录核对，指出需新增、更新、标记失效或仅复用的内容及其证据。缺乏证据的原因和方案标明未确定，不将推测写成已解决；没有可补录内容时明确报告。

主窗口按 project-corrections 规则将核实的结果写入完整记录并同步索引，保留问题表现、用户真实要求、最终采用的方案和验证状态。自行发现的问题注明发现来源，不能冒充用户的专门纠正。记录同步属于收尾步骤；普通案例不改写技能正文。审查者只复核本轮新增或修改的记录及受影响部分，不递归派发或重新执行整项任务。

修复实质问题后复验受影响部分。前端检查实际渲染和关键交互，文档检查最终文件。审查通过不能代替运行或产物证据。交付时说明产物、验证和剩余限制，区分本地完成、提交、推送和发布。

完成简报必须说明本轮记录变更。若新增或更新了条目，列出各自数量、编号、问题标题、此次新增的解决办法或修正内容、验证状态与链接，不能只写“已同步”。仅复用时注明复用编号；没有新增或更新时简要说明。若仍有同步受阻或待验证的条目，如实保留限制。
