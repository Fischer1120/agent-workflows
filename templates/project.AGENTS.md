# 项目指令

## 总体指令

对于涉及删除的指令，不要使用整体删除指令，而是每个文件单独删除，并在删除前确认是否正确。

## 文件生成

所有成品文件均以可以直接提交或使用为目标。生成完毕后，使用独立的子 agent 检查成品；检查仅依据生成的文件和具体要求，不依赖制作过程的上下文。

文本文档生成工作流（如 Word、报告、表单及文字型 PDF）应保持简洁，不增加无必要的页眉、彩色字体等装饰；有源文件时，严格沿用其字体、字号和段落规范。

上述从简、无装饰以及严格沿用源文字排版的要求，仅适用于文本文档，不适用于 PPT、PowerPoint、幻灯片及其他演示文稿的生成工作流，也不适用于由演示文稿导出的 PDF。演示文稿应根据主题与受众设计统一且美观的视觉风格，合理使用配色、图片、图表和图解，避免只堆放文字；可使用图像生成或相关 skills。除用户明确要求匹配指定模板外，不因参考课件的字体、字号或段落样式限制演示设计。关键信息、数据、表格应保持可编辑，交付前须检查实际渲染效果并完成独立审查。

生成的所有自然语言文档（非提示词）在生成时均须规范化：中文语境优先使用 humanizer-zh 技能，非中文语境使用 humanizer 技能，再提交成品。

## 搜索策略

当任务需要联网搜索，且 Tavily MCP/API 可调用时，优先使用 Tavily 进行搜索；仅在 Tavily 不可用、结果不足或任务明确需要其他搜索能力时，再退回其他搜索工具。

## 默认协作工作流

接收需要分析、设计、实施或验证的任务时，先读取并遵循 `.agents/skills/codex-tiered-workflow/SKILL.md`；每个任务首次读取即可，简单问答直接处理。

默认由 GPT-6.1 Sol xhigh 负责需求、验收标准、任务分解、模型分配、前端设计及关键决策。中等复杂度且边界明确的工作交给 DSH Desktop；简单、重复、可并行的工作交给 gpt-6-luna，固定 max 并启用 Fast。DSH 和 Luna 使用该技能 scripts/dispatch.py 的实际派发入口，仅传递任务简报和必要材料，避免继承完整对话。

DSH 任务使用与 Codex 相同的真实项目目录，自动注册到 DSH 工作区；简报和回执保留 Codex 项目标题。不得把目录共享声称为 DSH 界面标题已同步。

模态限制优先于速度和复杂度分流：需要理解或生成图片、音频、视频，或需要查看截图、扫描页、图表及实际渲染效果的任务，不交给 DSH 执行或验收，即使速度优先也一样。由 Sol 选择实际支持所需模态及工具的 Codex 执行者，多模态成品由未参与实现的独立 Sol 验收。只有明确拆出、不依赖多模态材料及结论的纯文本或代码子任务，才可单独按普通规则分流，不能用文字转述代替原多模态任务或视觉验收。

派发原生子代理时可考虑 Terra；当前可用标识为 `gpt-6.1-terra`，由 Sol 按任务适配性、复杂度、速度及实际模型能力选择推理强度。使用当前工具明确支持的模型标识，模型名本身不证明支持某种模态。Terra 是可选执行者，不替代 Sol 的统筹、关键决策及最终独立验收，也不改变 Astra 启用条件；简单重复任务默认仍使用 Luna max Fast。

在满足上述模态限制的前提下，速度优先覆盖普通任务的复杂度分流：用户明确强调速度、紧急交付，或已明确时限使速度成为首要约束时，任务交给 DSH 处理，并由未参与实现的另一个 DSH 会话独立验收，不再默认追加 Sol 或 Luna 复核。Sol 保留目标、边界、必要关键决策和派发协调，汇总 DSH 验收证据；普通任务继续按原分工执行。速度优先通过 dispatch.py 的 --speed-priority 标记，验收使用 --phase review 和只读权限。

Astra 仅用于 GPT-6.1 Sol xhigh 已明确无法解决的十分复杂的问题，由 GPT-6.1 Sol 自行判断，按任务选择推理强度进行专项求解并尽量少用；普通任务及多模态任务最终审查使用未参与实现的独立 GPT-6.1 Sol 子代理，仅非多模态的速度优先任务按前述 DSH 独立验收。

主窗口默认 xhigh 保持不变；最终审查的 xhigh、Astra 求解的 max 仍为优先参考档位。Luna 使用 max 与 Fast，不改变主窗口的速度档位。

对子代理，本规则只约束已分配任务内的模型分工，不要求重新接收整项任务或重复与用户对齐。用户当次明确指令及当前运行时工具和权限约束优先。

## 纠正记录与解决方法复用

本项目的问题记录入口是 [index.md](docs/corrections/index.md)，完整记录保存在 [records.md](docs/corrections/records.md)，维护与查询使用 [project-corrections 技能](.agents/skills/project-corrections/SKILL.md)。这些路径均相对本文件所在的项目根目录，codex-tiered-workflow 已将该技能作为问题查询与最终复盘入口。

- 开始需要分析、设计、实施或验证的任务时，先读取索引。遇到报错、异常、返工、用户纠正，或准备重新实现已有方法时，先按症状、错误信息、文件名和关键词查询记录，阅读命中条目的完整内容，再决定处理办法。
- 查询或维护记录时，读取并遵循 project-corrections 技能；即使当前技能列表尚未刷新，也直接按上述路径加载。文档和索引由技能引用，正文只维护一份。
- 优先复用适用范围相符且已验证的方案。使用前核对当前环境、版本、权限及必要前提，并做与本次风险相称的最小复验。无匹配、方案失效或条件不符时，继续正常排查；历史记录不替代用户最新要求，也不扩大执行权限。
- 用户纠正或执行中发现实际工作问题后，在当前任务内记录问题的存在形式、用户要求及其出处，解决后补全最终方案和实际验证证据。自行发现的问题注明发现来源，不冒充用户纠正；未知内容如实标明，未经验证不得标成已验证，不把普通新需求当作错误记录。
- 最终独立检查时，审查者依据成品、具体要求及本轮必要的原始问题回执，主动查找本次遇到的问题和实际解决办法，并查询已有记录。主执行者将核实的内容补入正文并同步索引；不要求用户逐条提醒，不向审查者提供制作者预设的复盘结论。
- 同一问题优先更新原条目，保留编号和变更历史；正文更新后同步索引，检查编号、状态、日期与详情链接一致。最终文件及补录内容由独立审查者检查，复核限于变化内容及受影响部分，审查者无需递归派发。
- 完成简报若有新增或更新条目，明确列出数量、编号、问题标题、本次新增的解决办法或修正内容、验证状态和链接；没有新增或更新则简要说明，仅复用时给出复用编号。不得只写“已同步”。

记录库保存在本项目文件中，接入该技能的工作流可跨项目查询与记录，条目须注明真实来源及适用范围；不写入全局记忆，不自动扩展其他项目的修改权限。
