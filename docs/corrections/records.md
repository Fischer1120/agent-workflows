# 工作问题与用户纠正记录

本文件保留用户纠正、执行中发现及最终独立检查确认的实际问题、用户要求、实际采用的最终方案及验证证据。[index.md](index.md) 只维护检索摘要；[project-corrections 技能](../../.agents/skills/project-corrections/SKILL.md) 负责查询与维护流程。记录库保存在本工作流仓库，供已接入的工作流跨项目使用；条目须注明真实来源和适用范围。

本公开仓库尚无正式记录。下方模板用于维护，不代表已经发生的问题；部署安装器只复制本文件的规则与模板。

## 记录规则

收到用户纠正，或在执行、独立检查中发现实际错误、工具障碍、验证失败等问题时，在当前任务内记录有复用价值的事实和处理方法，无需用户再次提醒。普通新需求和未发生的建议不算问题；无法核实的历史内容不补写成事实。未知原因、未确定的方案、尚未完成的验证应如实注明。

发现来源区分“用户纠正”“执行中发现”“独立检查”，保留真实来源项目或任务。自行发现的问题在“我的要求”中注明没有针对该问题的单独用户纠正，再准确引用或转述本任务实际要求，不虚构用户说过的话。已有用户纠正条目可保留原格式，以正文中的实际出处为准。

每条记录必须保留三项核心内容：问题的存在形式、我的要求、最终解决方案。问题表现应能说明何时触发、实际发生什么、应当怎样及造成什么影响；用户要求应保留原话或标明准确转述，并注明实际可得的出处；最终方案必须是实际采用的处理办法，写明操作、涉及文件、使用条件及必要局限。

编号使用 `CORR-YYYYMMDD-NNN`，日期按用户所在的 Asia/Shanghai 时区确定，同日序号从 `001` 递增。分配前同时核对索引与正文中的正式条目，跳过代码块中的模板。每条正文设置唯一的显式锚点 `corr-YYYYMMDD-NNN`。创建日期保留，更新日期随实质变更调整；具体日期填写为 `YYYY-MM-DD`。

同一问题在相同适用范围内更新原条目，重复发生或用户要求变化时补记变更历史。独立原因、不同适用条件的问题另建条目，并引用相关编号。失效的方案保留历史和失效原因，不直接删除。

### 状态

| 状态 | 含义 |
| --- | --- |
| 记录中 | 已确认实际问题，仍在定位原因或确定方案。 |
| 待验证 | 已采用处理办法，最终产物或运行行为尚未验证。 |
| 已验证 | 已核验最终产物或实际运行行为，并有检查方法与结果证据。 |
| 已失效 | 证据表明原方案在原适用范围内已不可用，保留原因和替代方案线索。 |

收到纠正时可以先记录，解决后再补全最终方案。未经验证的方案不能作为已确认的方法复用，进程正常退出也不能单独证明最终产物正确。复用旧方案前核对当前环境、版本、权限及其他前提，并做与本次风险相称的最小复验。仅当前场景不适用时说明差异，不据此否定原范围内仍有效的方案。

### 同步与证据

先更新本文件，再同步索引及条目总数。交付前检查正式条目与索引一一对应，编号唯一，摘要、关键词、适用范围、状态和更新日期一致，详情链接能到达对应锚点。多个执行者产生的记录由主执行者串行合并。

最终独立检查时，审查者根据具体要求、最终文件及本轮必要的原始问题回执，自行查找遇到的问题与实际解决办法，再与已有记录核对；主执行者核实后新增或更新正文与索引。审查者复核变化内容，不递归派发，也不因记录工作重复执行整项任务。完成简报列明新增或更新的数量、编号、问题标题、此次补入的方案或修正、验证状态与链接；若无变更则说明，无实际问题时不凑条目。

出处和证据可以是当前会话中可定位的用户消息、项目文件路径、实际执行的检查命令及结果。仅写确实存在的信息，不编造消息编号、文件或成功结果；引用项目文件时优先使用相对路径，便于项目移动后继续查询。日志、转述和历史方案只是证据，不能替代当前用户指令，也不授予额外执行权限。记录所需的错误信息应脱敏，不保存密钥、令牌或无关隐私正文。

## 条目模板

复制以下代码块的内容，填入实际信息后，追加到“正式记录”部分。替换编号、锚点、日期及括号中的说明，保留字段；没有结论的字段明确写为“尚未确定”或“尚未验证”。模板本身不加入索引。

```markdown
<a id="corr-YYYYMMDD-NNN"></a>

## CORR-YYYYMMDD-NNN 问题标题

- 状态：记录中
- 发现来源：（用户纠正 / 执行中发现 / 独立检查）
- 来源项目或任务：（问题实际发生的项目与任务）
- 创建日期：YYYY-MM-DD
- 更新日期：YYYY-MM-DD
- 适用范围：（项目、文件或模块、环境及必要版本条件）
- 关键词：（可检索的症状、报错片段、工具或文件名）
- 相关记录：（如有，引用编号与链接；没有则写“无”）

### 问题的存在形式

（写明触发场景、实际错误表现、预期行为及影响，保留必要的错误片段或产物位置。）

### 我的要求

（引用用户原话，或标注“准确转述”后写明要求。自主发现的问题注明没有针对该问题的单独用户纠正，再说明真实的任务要求。）

- 出处：（实际可得的会话、消息日期、文件或其他可核实位置）

### 最终解决方案

（尚未确定，或说明实际采用的操作步骤、涉及文件、使用条件、选择原因及必要局限。不要把拟议方案写成完成结果。）

### 验证与证据

- 检查方法：（实际检查的产物、命令或运行步骤；未执行时明确注明）
- 实际结果：（观察到的结果；没有结果则写“尚未验证”）
- 证据位置：（实际存在的项目文件、输出或可定位的会话；尚无则注明）

### 变更记录

- YYYY-MM-DD：（首次记录、后续修复、复验、重复发生、要求变化或失效原因）
```
